# Как выпустить версию

Обновления доставляет [Sparkle 2](https://sparkle-project.org). Установленное приложение раз в
сутки читает ленту

    https://raw.githubusercontent.com/pnazarovich/cribe/main/appcast.xml

и, если там появился выпуск свежее, предлагает его поставить. Ленту отдаёт сам GitHub —
отдельного хостинга у проекта нет. Архивы лежат в GitHub Releases.

В релизе всегда два файла:

| Файл | Кому |
| --- | --- |
| `Cribe-<версия>.dmg` | человеку, который ставит впервые |
| `Cribe-<версия>.zip` | Sparkle — по zip обновление ставится надёжнее |

---

## Разовый шаг: ключ подписи обновлений

Это делается **один раз за всю жизнь проекта** и только на машине владельца.

```bash
bash scripts/sparkle-tool.sh generate_keys
```

Утилита создаёт пару ключей ed25519, кладёт приватный в связку ключей macOS (в процессе
macOS спросит разрешение — это нормально, ключ ваш) и печатает публичный, например:

```
A public key has been generated and saved in your keychain. Add the following to your app's Info.plist:

    <key>SUPublicEDKey</key>
    <string>oCzO7…=</string>
```

Публичный ключ нужно вписать в `Info.plist` вместо заглушки:

```xml
<key>SUPublicEDKey</key>
<string>сюда_ваш_публичный_ключ</string>
```

Пока в `Info.plist` стоит заглушка (`AAAA…A=`), `scripts/release.sh` отказывается работать —
чтобы нельзя было случайно выпустить обновление, которое ни у кого не установится.

### Приватный ключ: где хранить и что будет, если потерять

По умолчанию `release.sh` берёт ключ **из файла** — так подпись не поднимает диалог связки
ключей на каждом выпуске. Выгрузить ключ из связки в файл:

```bash
bash scripts/sparkle-tool.sh generate_keys -x ~/.keys/cribe-sparkle.key
chmod 600 ~/.keys/cribe-sparkle.key
```

> **Файл с ключом хранится ВНЕ репозитория.** В `.gitignore` стоят `*.key` и
> `sparkle_private_key*`, но полагаться на это не стоит: держите ключ в стороне и сделайте
> резервную копию (менеджер паролей, зашифрованный диск).

> **⚠️ Потеря приватного ключа — самое дорогое, что здесь может случиться.**
> Публичный ключ вшит в каждую уже установленную копию приложения. Обновление, подписанное
> другим ключом, эти копии отвергнут. Значит, при утере ключа:
> - **обновления встанут у всех, кто уже поставил приложение** — навсегда;
> - новый ключ поможет только тем, кто скачает и поставит DMG заново, вручную;
> - вернуть старых пользователей на канал обновлений автоматически невозможно.
>
> Утечка ключа не менее опасна: с ним постороннему можно подсунуть вашим пользователям
> что угодно под видом обновления. Тогда — новый ключ, новая версия и просьба
> переустановить руками.

Если ключ вы держите только в связке ключей, запускайте выпуск так:

```bash
SPARKLE_KEY_SOURCE=keychain bash scripts/release.sh
```

Тогда `sign_update` спросит у связки пароль.

## Выпуск версии

### 1. Поднять номера в `Info.plist`

```xml
<key>CFBundleShortVersionString</key>
<string>0.2.0</string>   <!-- человеческая версия, её видно в «О программе» -->
<key>CFBundleVersion</key>
<string>2</string>       <!-- по нему Sparkle решает, что выпуск новее -->
```

`CFBundleVersion` **обязан расти**. Sparkle сравнивает выпуски именно по нему: забыли поднять —
обновления никто не увидит. `release.sh` это проверяет и откажется добавлять в ленту второй
выпуск с тем же номером сборки.

### 2. Написать, что изменилось

Файл `release-notes/<версия>.md`, например `release-notes/0.2.0.md`. Этот текст попадёт в окно
обновления — его читают пользователи, поэтому пишем по делу. Понимаются заголовки (`#`),
списки (`- `) и абзацы. Файла нет — `release.sh` остановится.

### 3. Собрать

```bash
DEVELOPER_ID="Developer ID Application: … (JC6637SY79)" \
APPLE_ID=… TEAM_ID=… APP_PASSWORD=… \
SPARKLE_PRIVATE_KEY_FILE=~/.keys/cribe-sparkle.key \
  bash scripts/release.sh
```

Сохранённый профиль notarytool у владельца называется `transcriber` — имя историческое, из-под
прежнего названия продукта; переименование продукта его не касается, и трогать профиль не нужно
(`NOTARY_PROFILE=transcriber bash scripts/release.sh` вместо трёх переменных Apple ID).

Скрипт соберёт `.app`, подпишет его вместе с вложенной Sparkle, нотаризует, приклеит степлер,
соберёт DMG, соберёт zip **уже со степлером внутри**, подпишет zip ключом EdDSA и допишет новый
`<item>` в `appcast.xml`.

Проверить машинку, не трогая ленту и не имея сертификата, можно сухим прогоном — он напечатает
то, что ушло бы в `appcast.xml`, но сам файл не изменит:

```bash
DEVELOPER_ID="-" SPARKLE_PRIVATE_KEY_FILE=… bash scripts/release.sh --skip-notarize
```

### 4. Выложить

1. Создать на GitHub релиз с тегом `v<версия>` и приложить **оба** файла из `dist/`.
   Имя zip менять нельзя — на него уже ссылается `appcast.xml`.
2. Убедиться, что zip скачивается по ссылке из `appcast.xml`.
3. Только теперь закоммитить и запушить `appcast.xml` в `main`.

Порядок важен: **пуш `appcast.xml` и есть момент выкладки обновления.** Если запушить ленту
раньше, чем файл появится в релизе, пользователи получат ошибку загрузки.

## Как проверить, что обновление видят

### До выкладки — на локальной ленте

Ставить обновление поверх рабочей копии в `/Applications` не надо: проверяйте на копии.

```bash
T=/tmp/update-test
P=/usr/libexec/PlistBuddy

# 1. отдельная копия приложения ПРЕДЫДУЩЕЙ версии
mkdir -p $T/feed && ditto dist/Cribe.app $T/Cribe.app

# 2. подменить у копии ленту, ключ и bundle id
$P -c "Set :SUFeedURL http://localhost:8791/appcast.xml"  $T/Cribe.app/Contents/Info.plist
$P -c "Set :SUPublicEDKey <публичный ключ тестовой пары>" $T/Cribe.app/Contents/Info.plist
$P -c "Set :CFBundleIdentifier online.nazarovych.cribe.updatetest" \
                                                          $T/Cribe.app/Contents/Info.plist
# без этого ATS не пустит обычный http даже на localhost
$P -c "Add :NSAppTransportSecurity dict"                          $T/Cribe.app/Contents/Info.plist
$P -c "Add :NSAppTransportSecurity:NSAllowsLocalNetworking bool true" $T/Cribe.app/Contents/Info.plist
codesign --force --deep --sign - $T/Cribe.app

# 3. локальный сервер с лентой и архивом «новой» версии
cd $T/feed && python3 -m http.server 8791

# 4. запустить копию: плановая проверка сработает сразу после старта
open -n $T/Cribe.app
```

Три вещи, на которых легко споткнуться:

- **Свой `CFBundleIdentifier` у копии обязателен.** Иначе копия пишет настройки в домен
  установленного Cribe и портит их — там же лежит и «когда проверяли в прошлый раз».
- **`NSAllowsLocalNetworking`** — без него запрос к `http://localhost` молча не уходит.
- Правка `Info.plist` ломает подпись, поэтому копию пересобираем ad-hoc. Раздавать такую копию,
  разумеется, нельзя.

Чтобы проверка сработала сразу, а не через сутки, «последнюю проверку» сдвигают в прошлое:

```bash
defaults write online.nazarovych.cribe.updatetest SULastCheckTime \
  -date "2020-01-01 00:00:00 +0000"
```

Обновление, найденное **сразу после запуска**, Sparkle показывает окном поверх всего.
Найденное позже — не показывает вовсе: оно ждёт строкой в меню (это и есть «мягкое
напоминание», см. `Sources/Cribe/Updater.swift`). Оба поведения — норма, а не ошибка.

### После выкладки

```bash
curl -s https://raw.githubusercontent.com/pnazarovich/cribe/main/appcast.xml | head -40
```

Лента отдаётся через CDN GitHub и обновляется не мгновенно — до пяти минут. Дальше в самом
приложении: **Проверить обновления…**. Плановая проверка идёт раз в сутки, и найденное
обновление приложение не выбрасывает окном поверх работы, а вешает строкой в меню —
«Обновление 0.2.0 — установить…».

Что происходит на стороне пользователя, видно в журнале:

```bash
log show --predicate 'subsystem == "org.sparkle-project.Sparkle"' --last 1h
```
